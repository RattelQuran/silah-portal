## ترتيب النشر المقترح (كل خطوة بموافقتك)
1. ✓ **D-12 (2026-11-25):** قُرئت المنشورة وقورنت، واختُبرت الواجهتان عليها. **دمج PR #2 لا يتوقف على نشر القواعد**، فالواجهة الجديدة تعمل على المنشورة كما هي.
2. **نسخة احتياطية قبل أي دمج.** زر النسخ غير موجود في الإنتاج بعد، لأنه ضمن PR #2. فأمامك طريقان مجانيان:
   - **(موصى به)** تشغيل الفرع على جهازك على `localhost` (النطاق مسموح لتسجيل الدخول)، ثم الدخول بحساب المالك وضغط «تنزيل نسخة احتياطية». هذه عملية **قراءة فقط** من الإنتاج، وتحتاج موافقتك، وأرسل لك الأمر.
   - أو دمج PR #2 أولًا: الدمج يغيّر الواجهة فقط ولا يلمس البيانات ولا القواعد، ثم أخذ النسخة من الزر قبل أي خطوة أخرى.
   - التصدير من Google Cloud يحتاج خطة Blaze المدفوعة، فهو غير مقترح.
3. **دمج PR #2** في `main`. هذا ينشر الواجهة على GitHub Pages، ولا يغيّر القواعد.
4. **(تحسين، بانتظار موافقتك)** نشر القواعد المقترحة النهائية، ومعها قفل D-17. الخطوات التفصيلية قبل النشر وبعده والرجوع في SECURITY_AUDIT_FINAL.md §7. أبلغ المحاسب أن الاعتماد سيقفل الشهر على المعلمة، وقد ضُيّقت (RULES_DIFF.md)، وتعمل مع الواجهتين الحالية والجديدة: `firebase deploy --only firestore:rules --project silah-portal`، منك أو بموافقتك. ويُحفظ قبلها النص الحالي في ملف للرجوع.
5. **فحص بعد النشر:** دخول كل دور مرة، وتسجيل حضور تجريبي ثم إلغاؤه، وطلب تجريبي من نموذج الموقع.
6. **دمج الاتجاه D** (`web4d/signature-preview`) بعد اعتمادك النهائي.
7. **D-15 App Check:** خطوات Console واحدة واحدة، ثم دمج الفرعين دون فرض، ثم مراقبة 48 إلى 72 ساعة على الأقل بشروط، ثم الفرض بموافقة منفصلة. الخطة في APP_CHECK.md. App Check لا يغني عن الخطوات 1 إلى 4.

## الرجوع عند المشكلة
- الواجهة: `git revert` لدمج الفرع، أو إعادة `main` إلى `restore/2026-11-25-pre-web4d`. GitHub Pages يعيد النشر خلال دقائق.
- القواعد: `docs/rules-deployed-2026-11-25.rules` هو نقطة الرجوع، ويُلصق في Console › Rules ثم Publish.
- البيانات: الاستعادة من ملف النسخة الاحتياطية، مع المعاينة، ودون استبدال افتراضيًا.
