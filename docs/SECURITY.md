# SECURITY — قواعد الأمان والصلاحيات

## الحالة باختصار
| البند | الحالة |
|---|---|
| القواعد المنشورة في الإنتاج | **غير معروفة المحتوى.** القراءة المجهولة مغلقة (فحص REST في 2026-11-25: ثماني مجموعات أعادت 403) |
| `firestore.rules` في المستودع | **مقترحة وغير منشورة.** كُتبت من سلوك التطبيق الفعلي، واختُبرت في المحاكي |
| المطابقة بين المقترحة والمنشورة | **لم تُفحص.** تحتاج نص القواعد المنشورة من المالك |

## المطلوب من المالك لإغلاق S-1
1. افتح Firebase Console › مشروع `silah-portal` › Firestore Database › تبويب **Rules**.
2. انسخ النص كاملًا والصقه في المحادثة.
3. سأقارنه بالقواعد المقترحة وأكتب الفروق. **النشر يكون منك أو بموافقتك فقط**، بأمر: `firebase deploy --only firestore:rules --project silah-portal`.

## ضمانات مختبرة
- **لا رفع للصلاحيات ذاتيًا:** إنشاء `users/{uid}` يقبل فقط دور الدعوة نفسه وteacherId وstudentIds نفسيهما، أو admin لبريد المالك المؤكَّد. ولا يعدّل الملف بعد ذلك إلا المدير.
- **البريد غير المؤكَّد** لا يحصل على دور المالك.
- **عزل المعلمات:** لا تقرأ المعلمة ولا تكتب إلا سجلات طلابها، ولا ترى أي مبالغ، ولا تنشر تقريرًا شهريًا، ولا تعدّل أجرها.
- **عزل أولياء الأمور:** لا يرى ولي الأمر إلا أبناءه، والتقارير الشهرية المنشورة فقط، ولا يكتب شيئًا.
- **فصل الأدوار الإدارية:** الحسابات لا تمس الطلاب ولا الحضور، والإشراف لا يرى المال.
- **نموذج الموقع:** إنشاء فقط، بالحقول الأحد عشر، وبأنواع وأطوال وقيم محددة، وحالة `new`. لا قراءة ولا تعديل ولا حذف للزائر.

## نقاط مفتوحة
- **S-3:** لا حد لمعدل إرسال نموذج الموقع. القواعد تمنع البيانات المشوهة لا الإغراق. الحل المجاني: Firebase App Check مع reCAPTCHA v3، وهو مجاني ضمن الحصة. يحتاج تفعيلًا من المالك في Console.
- `ownerEmail()` في القواعد يجب أن يطابق `config.js → ownerEmail`.
- عند تغيير عقد نموذج الموقع، حدّث قاعدة `registrations` والاختبار معًا.

## تشغيل الاختبارات
```sh
cd tests && npm install
npm run rules      # 18 اختبارًا للقواعد في محاكي Firestore
npm run emulator   # البوابة الحقيقية + المحاكي: دخول الأدوار الخمسة برابط البريد
```
المحاكي يعمل بمشروع `demo-silah`، ولا يتصل بالإنتاج.
